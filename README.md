# DSCI 320 Dataset Explorer

A searchable, filterable catalog of datasets for DSCI 320. A tool that lets students filter datasets by column type, search by topic using semantic embeddings, and see ML generated suitable results instead of browsing datasets by hand.

## Project structure

```
dsci320-dataset-explorer/
├── data/
│   ├── verified/               Verified answer key CSVs, confirming true column types (name must match the file in raw/)
│   ├── metadata/              Result of script including column classifications
│   ├── raw/                   Locally downloaded datasets as CSV files
│   ├── raw_test/              A test folder of sample data
│   └── tracked/               Includes a log of all processed data tables compared to the verified answer keys
├── src/
│   ├── classifier.py              defines classify_column() that guesses a column's type
│   ├── build_classifications.py   runs the classifier across data/raw, writes column_classifications.csv
│   ├── build_tracker.py           compares classifications against data/verified, writes dataset_tracker.csv
│   ├── ml_tagger.py               defines tag_ml_suitability(), infers ML task tags from column counts/cardinality
│   ├── build_ml_tags.py           runs the tagger across data/raw, adds ml_tags/ml_reasons to dataset_tracker.csv
│   ├── build_site_data.py         converts dataset_tracker.csv to docs/data.json, adds a description embedding per dataset
│   └── main.py                    runs the full pipeline in order
├── dataset_tracker.csv        hand-maintained source_url/description per dataset (never written by the pipeline)
└── docs/                      the actual website (served via GitHub Pages)
    ├── index.html
    ├── data.json               generated by build_site_data.py, fetched by the site at runtime
    ├── css/style.css
    └── js/
        ├── app.jsx                 top-level component: fetches data.json, holds filter/search state
        ├── clientClassifier.js     JS port of classifier.py, used by the upload modal
        ├── semanticSearch.js       loads the embedding model in-browser for search
        └── components/             Topbar, Card, FilterBar, DatasetDetail, UploadModal
```

## Setup

```
# from project root
python3 -m venv venv
source venv/bin/activate
pip install pandas sentence-transformers
```

`sentence-transformers` pulls in PyTorch — a much larger install than pandas alone, and the
first pipeline run downloads the `all-MiniLM-L6-v2` model weights (~90MB, cached afterward).

Every new session, re-activate the environment before running with:
```
source venv/bin/activate
```

## Running the pipeline

From the project folder:
```
cd src
python main.py
```

This runs all four steps in order: classify columns, build the tracker, add ML tags, write docs/data.json.

Raw files over a few hundred MB are sampled rather than read in full (`SAMPLE_ROW_LIMIT = 8000` in
build_classifications.py and build_ml_tags.py) so the pipeline stays fast. Counts for verified
datasets come from the verified CSV instead and aren't affected by sampling.

## Running the dev site

The site is plain HTML/JS with no build step — React, Babel, PapaParse, and transformers.js all
load from CDNs in index.html. Because it uses `fetch()` and an ES module (semanticSearch.js), it
has to be served over HTTP, not opened directly as a file:

```
cd docs
python3 -m http.server 8080
```

Then open `http://localhost:8080`. The search box needs a few seconds on first load to download
the embedding model (~90MB, cached by the browser afterward).

## Naming rule
*data/raw/X.csv* must match *data/verified/X.csv* exactly for scoring to work. The `name` column
in the root dataset_tracker.csv must also match (without the .csv), or a dataset's source_url and
description won't merge in during build_tracker.py.
